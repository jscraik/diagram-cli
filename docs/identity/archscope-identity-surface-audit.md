## Classification Rules

- `canonical-now`: active user-facing or agent-facing surfaces that should lead
  with `Archscope`, `archscope`, and architecture evidence language.
- `compatibility-labelled`: active surfaces where old names are correct because
  they name the package, repository, compatibility command, `.diagram`,
  `.diagramrc`, migration evidence, or schema paths.
- `deferred-rename`: surfaces that must not be renamed until a dedicated
  migration spec approves the change.
- `historical-context`: old specs, plans, snapshots, fixtures, or migration
  records that may preserve earlier wording because they document prior state.

## Historical and Deferred Surfaces

The broad identity search includes historical plans, specs, fixtures, test
descriptions, and migration records. These should not be rewritten during this
plan unless they are active product docs or generated current user output.

Examples:

- `docs/plans/**` and `docs/specs/**` before this plan: `historical-context`.
- `docs/migration/archscope-compatibility.md`: `compatibility-labelled`.
- `.diagram/**` migration evidence and contract files: `deferred-rename`.
- Tests that assert legacy compatibility or fixture names: `historical-context`
  or `compatibility-labelled` unless the expected active output changes.
- Source identifiers such as `diagramRc`, `diagramType`, and Mermaid diagram
  terminology: domain terms, not product-identity drift.

## P1-P4 Work Queue

P1 should focus on first-read docs only:

- confirm `README.md`, `docs/getting-started.md`, `docs/cli-reference.md`,
  `docs/architecture-testing.md`, and `docs/README.md` are Archscope-first;
- keep package, repository, `.diagram`, and `.diagramrc` compatibility facts;
- avoid rewriting historical specs, plans, and migration records.

P2 should focus on CLI-facing product text:

- `src/diagram.js`;
- `src/commands/init.js`;
- active command recovery hints in `validate`, `diff`, `generate`,
  `generate-animated`, and `workflow pr`;
- `package.json.description` if updated tests prove the metadata change is
  safe.

P3 should focus on generated human output and repository templates:

- `.github/workflows/pr-impact-comment.yml`;
- `.github/ISSUE_TEMPLATE/feature.yml`;
- `.github/ISSUE_TEMPLATE/issue.yml`;
- generated evidence tests only if active output changes.

P4 should create the rename-readiness record and keep these hard renames
blocked:

- package rename away from `@brainwav/diagram`;
- repository rename away from `jscraik/diagram-cli`;
- artifact namespace rename away from `.diagram`;
- config rename away from `.diagramrc`;
- schema or machine-field rename solely for branding.
